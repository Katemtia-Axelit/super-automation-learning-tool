## 三、Planner 重构方案要点

### 3.1 当前架构缺陷（溯源）

| 问题 ID | 描述 | 代码位置 | 严重度 |
|---------|------|---------|--------|
| **3.1** | 双状态机：抽卡页 timerDockSession + 任务页 timerActiveSession，两套独立 interval | `385:388`, `2414:static/app.js` | **高** |
| **3.2** | 暂停本地模拟：改写 started_at，刷新后暂停状态丢失 | `456:469:static/app.js` | **高** |
| **3.8** | initTimerDock 中 loadTimerDockActive() 是 async，clearInterval 与它有 race condition | `390:395:static/app.js` | **高** |
| **3.6** | 任务页计时器不支持暂停，刷新后从 API 加载时无暂停状态 | `2446:2449:static/app.js` | **中** |
| **3.4** | stopTimerFromDock abandoned 任务无后续处理（是否入弃牌堆？） | `477:496:static/app.js` | **高** |

### 3.2 三套方案对比

| 方案 | 描述 | 改动量 | 优点 | 缺点 | 风险 |
|------|------|--------|------|------|------|
| **方案 1：前端单例** | 全局 TimerManager 类，统一状态，localStorage 临时存储暂停 | ~120-150 行 | 改动小，可止血 | 刷新丢暂停，多 tab 不同步 | **中** |
| **方案 2：后端持久化** | 新增 pause/resume API，数据库新增 paused_at/total_paused_ms 字段 | 后端 80 + 前端 100 行 | 根本解决刷新丢暂停 | 需数据库迁移，有幂等性问题 | **高** |
| **方案 3：混合方案** | TimerManager 单例 + 后端 API + localStorage failover | ~280 行 | 兼顾速度与持久化 | 复杂度最高，开发周期长 | **高** |

## 五、优先处理事项（Top 3）

基于三子代理审查结果，建议最优先处理：

### 🥇 第一优先：计时器状态统一（高 ROI）

**理由**：
- Planner 提供了 5 步可落地实施路径，Step 1 仅需 5 行即可止血
- 双状态机（3.1）影响用户日常使用最频繁的功能
- 修复后可为其他区域重构提供参考模式

**行动**：
1. 立即修复 interval race condition（5 行）
2. 引入 TimerManager 单例统一两套状态（100 行）
3. 后端新增 pause/resume API 持久化暂停状态

### 🥈 第二优先：completeWithFeedback 重复 API 调用（M1）

**理由**：
- Auditor 发现的漏报，严重度**高**
- 已完成任务是否能再移入弃牌堆，后端逻辑不明确
- 可能导致数据库状态污染

**行动**：审计后端 `/api/tasks/{id}/move-to-discard` 对已完成任务的行为，必要时加防护或明确业务规则

### 🥉 第三优先：XSS 风险（1.5 + M2）

**理由**：
- task.name 直接插入 innerHTML（M1.5）
- mdToHtml 代码块内容未转义（M2）
- 安全底线问题，虽概率低但需修复

**行动**：
1. 引入 `escapeHtml()` 工具函数
2. 对 task.name/description 做 HTML 转义后再拼接
3. mdToHtml 代码块内容也需转义

## 1. 安全违规修复：E2E 隔离验证器读取并哈希生产数据库

### 1.1 违规事实

`scripts/run_e2e_isolated.js` 的 `fingerprintFile()` 使用
`fs.readFileSync()` **读取**真实生产文件并计算 SHA-256：

```javascript
// 修复前的实现（已删除）
function fingerprintFile(absPath) {
  const stat = fs.statSync(absPath);
  const hash = crypto.createHash('sha256');
  hash.update(fs.readFileSync(absPath));   // ← 读取生产 DB 内容
  return { path: absPath, exists: true, size: stat.size,
           mtimeMs: stat.mtimeMs, sha256: hash.digest('hex') };
}
```

被读取的受保护路径：

- `data/task_publisher.db`
- `data/task_publisher.db-wal`
- `data/task_publisher.db-shm`
- `config/config.json`
- `src/notes/**`（递归逐文件，`fingerprintTree()`）

### 1.2 为什么这是违规

项目最高数据保护要求（见 `.cursor/rules/data-redlines.mdc`）是：

> **不读取、不写入、不复制、不哈希、不恢复**真实生产 SQLite 数据库及其
> WAL/SHM。

"运行前后哈希一致"这一证明方式本身**要求先读取一次生产文件**。用读取来
证明"没有变化"，本身就是一次读取 —— 证明手段与被保护的对象冲突。

### 1.3 修复方式：三重证明，全程不打开任何生产文件

| 层 | 文件 | 机制 | 时机 |
|---|---|---|---|
| **A. 事前阻断** | `scripts/guard/protected_paths_guard.js` | 包装 `fs.readFileSync` / `openSync` / `createReadStream` / `readdirSync` / `readlinkSync` / `realpathSync` 及 `fs.promises.readFile/open/readdir`；对 `data/**`、`config/**`、`src/notes/**` 的任何访问尝试 **立即抛错**（`SAL_ISOLATION_VIOLATION`） | runner 启动时安装，覆盖 runner 及其子进程内的 fs 调用 |
| **B. 事中记录** | `tests/e2e/synthetic_audit.py` | 在合成服务器 **进程内** 安装 `sys.addaudithook`，记录真实发生的 `sqlite3.connect`、`open`、`os.listdir`、`os.scandir`、`os.stat` 目标路径；判定"是否落在真实项目的受保护区""SQLite 是否越出合成根" | 合成服务器启动前安装，随进程生命周期持续记录 |
| **C. fail closed** | `tests/e2e/synthetic_root_selfcheck.py` | 启动前断言：合成根 ≠ 真实项目根、两者互不包含、解析出的 db / notes / config 路径全部落在合成根内；任一不成立 **拒绝启动** | 合成服务器 spawn 子进程之前 |

**关键差异**：修复后 runner **不再对生产路径发起任何 fs 调用**。隔离性由
"路径守卫 + 进程内审计 + 启动自检"证明，而不是由"读取后比对"证明。

### 1.4 合成服务器接线

`tests/e2e/factory-sandbox-server.py` 新增：

- `_install_synthetic_bootstrap()` —— 把审计模块与启动包装脚本复制进合成根；
- `_child_env()` —— 注入 `SAL_AUDIT_REAL_ROOT` / `SAL_AUDIT_SYNTHETIC_ROOT` /
  `SAL_AUDIT_OUTPUT`；
- `_self_check()` —— 启动前 fail closed 自检；
- 子进程由 `python -B _sandbox_bootstrap.py` 启动（不再是 `run_app.py`），
  包装脚本先装审计钩子再 `runpy` 执行 `run_app.py`（同进程，PID 不变）。

### 1.5 机械守卫

`tests/characterize/test_e2e_isolation_guard.py`（**17 项**，全绿）锁定上述
机制，使"隔离方式"不会在后续重构中被悄悄改回"读生产文件比对哈希"：

- runner 源码中不得出现 `createHash('sha256')` / `fingerprintFile` /
  `fingerprintTree` / 生产路径拼接读取；
- runner 必须安装守卫、必须断言审计无违规；
- 审计清单路径必须由 **合成根** 拼出；
- 守卫自检：受保护路径全部拦截、合法路径全部放行、真实触发时确实抛错；
- 自检脚本：真实项目根 / 嵌套根 / 越界路径 三种情况必须被拒绝；
- 合成服务器源码必须真的安装 bootstrap 与自检、必须传递审计环境变量。

## 2. 表述纠错一：`SAL_ENFORCE_AGENT_POLICY` 的实际启动安全状态

### 2.1 P1 Handoff §5.1 的原表述与其不准确之处

原文：

> "`SAL_ENFORCE_AGENT_POLICY` 默认关闭（既有业务特征套件在合成根里不带策略
> 就直接 POST `/api/gacha/*` 等，默认开启会让它们全挂）。因此 **正式部署目前
> 并未获得服务端保护**，浏览器引导守卫仍只是 UI 层。"

**前半句正确，后半句不准确。**

### 2.2 实际代码事实

`server/app/app_factory.py`：

```python
app.config.setdefault(
    ENFORCE_CONFIG_KEY,
    os.environ.get(ENFORCE_ENV_VAR, "") == "1",
)
install_bootstrap_gate(app, app.config["_agent_policy_dir"])
```

即：**Factory 的默认配置**在环境变量未设置时关闭服务端闸门 —— 这一点属实。

但正式启动链并非如此。`scripts/launch_server.py`：

```python
def build_child_env(base=None):
    env = dict(os.environ if base is None else base)
    env[ENFORCE_ENV_VAR] = "1"      # ← 强制开启，父进程无法关闭
    return env
```

且 `main()` **拒绝** legacy 后端（`LEARNING_TOOL_BACKEND=legacy` 直接
`SystemExit`），只允许 Factory。

### 2.3 修正后的准确表述

| 场景 | 服务端闸门状态 |
|---|---|
| **官方安全启动链**（`scripts/启动学习工具.bat` → `start_web_safe.bat` → `launch_server.py`） | **强制开启**。`build_child_env()` 把 `SAL_ENFORCE_AGENT_POLICY=1` 注入子进程环境，父进程即便设为 `0` 也被覆盖 |
| 绕过启动器直接 `python run_app.py` | 关闭（Factory 默认配置） |
| 合成测试环境 | 关闭（无策略，否则既有特征套件全挂） |

> **结论**：正式部署 **通过官方启动器运行时是拥有服务端保护的**。
> P1 Handoff 的"正式部署目前并未获得服务端保护"表述 **仅对绕过启动器的
> 直接运行成立**，属于以偏概全。

### 2.4 P2 的处理

- **不改动任何安全机制**：闸门逻辑、423 状态码、路径前缀集合、Publisher
  语义一律保持。
- P2 交付说明中按本节表格如实记录。
- 本纠错 **不是** P1 合同变更，仅是交付说明的事实澄清。

## 3. 表述纠错二：Schema 的「14 + 1」归属

### 3.1 事实

`server/schema/__init__.py::REQUIRED_TABLES` 恰好包含 **14 张**业务表：

```
tasks, tags, task_tags, task_dependencies,          (4, 任务域)
gacha_records, task_rejection_log,                  (2, 抽卡域)
timer_sessions,                                     (1, 计时器域)
daily_user_state, state_assessments,
user_schedule, daily_schedules, activities,          (5, 状态/日程域)
task_feedback_events, task_completion_feedback      (2, 反馈域)
```

`free_task_events` **不在**其中。它由
`server/services/free_task_events.py::FreeTaskEventStore` 自行建表，
因为它带有 **append-only 触发器** 与 **部分唯一索引** 语义；由
`ensure_all` 统一创建会破坏其追加语义。

### 3.2 修正后的准确表述

> **14 张集中 Schema 管理的表 + 1 张由专用 Store 自主管理的表**
> （`free_task_events`，append-only，由 `FreeTaskEventStore` 自管）。

不得笼统声称"15 张表全部属于 `server/schema/`"。

### 3.3 P2 的处理

- P2 迁移后的数据访问 **必须** 继续遵守该边界：`server/schema/**` 是唯一
  DDL 处；`free_task_events` 的建表与写入仍只由 `FreeTaskEventStore`
  负责。
- P2 将新增断言测试，机械校验"14 张表由 `ensure_all` 建立 +
  `free_task_events` 不在 `REQUIRED_TABLES` 中且由专用 Store 自管"。

## 4. 保留为待用户裁决的产品语义：Gacha 策略系数方向

### 4.1 事实

P1 已将抽卡核心算法与编排下沉到 `server/services/gacha.py`，并保留
100,250 组 Golden 证据（`max_diff = 0.000e+00`）。

历史注释、Protocol 描述与实际加权抽样之间存在 **权重方向解释不一致**：

- 实际行为：权重 **越小越容易被抽中**；
- 策略系数：`max(0.01, base * factor)`，类别系数 × 卡类型系数 **正交相乘**；
- 部分文档/注释把系数描述成"越大越容易"，与实际相反。

### 4.2 P2 的处理原则（已执行）

- **保留现有实际行为** —— 不修改权重算法、不修改乘法方向、不重新设计抽卡概率；
- **继承 P1 的 100250 组 Golden 证据**，`max_diff` 必须保持 0；
- 不因注释存在矛盾就改变产品语义。

### 4.3 待用户裁决

> "策略系数越大越容易被抽中 / 越大越不容易被抽中"这一 **产品语义表述**
> 属于 **未由用户裁决** 的事项。P2 **不自行裁决**，作为公开未决项移交。

**具体问题**：当用户把某类别的策略系数调大时，期望该类别的卡
**更容易**被抽中，还是 **更不容易**？

**技术现状**：当前实际实现是 `weight = max(0.01, base * factor)`，权重越小
越容易被抽中，因此 **系数调大 → 实际更难被抽中**。

**如果裁决结果与当前行为不一致**，则需要修改 `server/services/gacha.py` 的
`apply_policy_coefficients()`，并同时更新 100,250 组 Golden 基准 —— 属
于 P2 之后的独立变更，不在本里程碑内。

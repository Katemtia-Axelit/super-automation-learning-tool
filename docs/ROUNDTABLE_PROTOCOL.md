# 圆桌协议 (Roundtable Protocol)

> **本文件是圆桌会议的规范权威。** Issue 是**过程权威**（讨论与分歧在此），
> `docs/ROUNDTABLE_<date>.md` 是**结论权威**（已定案落此），tag 是**时间锚点**。
> 三者各司其职，避免「只留转录板」或「只留无来源的结论」。

**版本**：v1（2026-11-27 建立）
**适用范围**：本仓库内发起的全部多席位（多模型 / 多 Agent）结构化讨论。

---

## 1. 为什么用 Issue

**选择本仓库 Issue，不启用 Discussions，不开独立仓库。**

理由：

- 与里程碑提案、想法在同一现场，评审路径统一；
- 已有先例（`AI-Practical-Training/issues/1`）；
- 全部 **PUBLIC 明牌**——讨论过程公开可查，不存在「黑箱会议」；
- 标签体系已设计（见 §6）。

**已知代价**：Issue 没有原生「席位」概念，且历史上出现过「Issue 退化为转录板」的缺陷。
§4 的三条机制专门修补这一点。

## 2. 席位

### 2.1 席位标识

席位标识必须用**固定席位名**或 **conversation UUID**。

**禁止用 Tab 序号**（`席位 1`、`席位 2`）——Tab 顺序会因内容长度变化而漂移，
导致同一席位在不同轮次被识别为不同席位。

标准席位：

| 席位 | 职责 | 典型输出 |
|---|---|---|
| `chair` | 主持、收敛、宣布结束 | 议程、收敛结论、结束评论 |
| `architect` | 架构与实现路径 | 分层方案、接口、迁移步骤 |
| `critic` | 反对意见与风险 | 反例、失败模式、隐藏代价 |
| `analyst` | 证据、基线与数据 | 实测输出、门禁结果、数据核对 |

可以按需增补席位（如 `product`、`security`），但**必须在会议开场时登记在 Issue 正文中**。

### 2.2 席位身份与评论作者

**席位 Agent 必须自己发自己的评论。**

- 每条评论的**作者**必须与评论头里声明的 `[席位]` 一致；
- 编排器（orchestrator）**只负责**：读取全部评论 → 注入下一轮提示词 → 派发任务；
- 编排器**不得**代写评论内容、**不得**代发评论。

> 这是对「转录板」缺陷的**结构性防御**：编排器产出的评论没有自己的席位头，
> 因而不合规、不会被采信。

### 2.3 权限最小化的已知局限

理想形态是**每席位一个只对单一 issue 有 comment 权限**的账号 / 机器用户。

当前是**单账号方案**，因此存在一个明确局限：

> **任何有写权限的一方都能以任意席位身份发表评论。** 评论头是**约定**，
> 不是**密码学身份**。当前唯一的缓解手段是：
> 1. 外部写操作审计日志（§7）；
> 2. 最小 token scope；
> 3. 幂等键一致性（§5）使得「代发」至少不能绕过重复检测。

在实现「每席位独立账号」之前，**不得**把评论头当作信任边界使用。

## 3. 轮次

### 3.1 轮次计划

会议开始时，chair 必须在 Issue 正文登记**轮次计划表**：

| 轮次 | 主题 | 预期产出 |
|---|---|---|
| 1 | 现状与问题界定 | 各席位独立判断，不互相对话 |
| 2 | 方案展开 | 各自提出路径 |
| 3 | 交叉质询 | 回应他人观点 |
| 4 | 收敛 | chair 汇总 |

**第 1 轮必须独立**：席位之间先各自成文，避免第 1 轮就互相锚定。

### 3.2 轮次推进

- 每轮结束后由 chair 决定是否推进；
- 轮次号写进评论头 `[轮次]`；
- 会议可以延长轮次，但**不得**回填已结束轮次的评论（回填会破坏幂等键语义）。

## 4. 三条修补机制（对应历史缺陷）

| 历史缺陷 | 修补机制 | 可验证判据 |
|---|---|---|
| **编排器代发评论 → 变转录板** | 席位 Agent 必须自己发自己的评论；编排器只做「读全部评论 → 注入下一轮提示词」，不得代写评论内容 | 每条评论作者与声明席位一致；编排器日志中无「代发」动作 |
| **席位身份用 Tab 位置序号（不稳定）** | 席位标识必须用固定席位名或 conversation UUID，禁用 Tab 序号 | 评论头部不出现数字序号；同一席位跨轮次名字不变 |
| **幂等键签名不一致**（"已发过"误判为 blocked） | 幂等键统一定义为 `sha256(会议ID + 轮次 + 席位名 + 内容前 N 字符)`；编排器 / 发言器 / 日志**必须使用同一函数实现** | 同轮重跑不产生重复评论；「blocked」与「already posted」可区分 |

---

## 5. 幂等键

### 5.1 定义

```text
idempotency_key = sha256( meeting_id + "|" + round + "|" + seat + "|" + first_N_chars_of_body )
```

其中 `N = 128`（正文前 128 个字符），`meeting_id` 为 `RT-<YYYYMMDD>-<nn>`。

**编排器、发言器、审计日志必须调用同一个函数**（同一份代码），
不允许各自实现一遍——签名不一致正是历史缺陷的根因。

### 5.2 用法

- 评论头 `[幂等键]` 写 **sha256 前 16 位**；
- Issue 置顶评论列出**每席每轮的幂等键**，供人工核对；
- 重跑同一轮时，命中已有幂等键 → 状态是 `already posted`，
  **不是** `blocked`。二者必须能区分：
  - `already posted` — 该席该轮已发言，属正常去重；
  - `blocked` — 该席该轮**不应**发言（前一轮未完成 / 阶段不匹配 / 权限不足）。

## 6. 标签与编号

### 6.1 Issue 编号

| 事务 | 标题前缀 | 模板 |
|---|---|---|
| 圆桌会议 | `[RT-<YYYYMMDD>-<nn>]` | `.github/ISSUE_TEMPLATE/roundtable.md` |

`nn` 为当日序号，两位，从 `01` 起。

### 6.2 标签

| 标签 | 含义 |
|---|---|
| `type:roundtable` | 事务类型 |
| `stage:proposal` | 已登记，尚未开始 |
| `stage:approved` | 已批准进入会议 |
| `stage:shipped` | 会议结束且摘要已入库 |

---

## 7. 评论格式（强约束）

每条席位评论**必须**以固定头部开始：

```text
[席位] architect
[模型] claude-opus-5.5
[轮次] 1
[会议] RT-20261127-01
[幂等键] <sha256 前 16 位>
[回复对象] <comment-id 或 none>

<正文>
```

**不合规评论视为无效发言，编排器不采信。**

- `[回复对象]` 填所回应评论的 comment-id（GitHub 数字 id），或 `none`；
- 正文与头部之间空一行；
- 头部字段顺序固定，便于机器解析。

## 8. 外部写操作审计

**所有对 GitHub 的写操作**都必须记入
[`external-write-log.md`](external-write-log.md)：

| 操作类型 | 计入 |
|---|---|
| `gh issue create` / `gh issue comment` / `gh issue close` | ✅ |
| `gh pr create` / `gh pr comment` / `gh pr merge` | ✅ |
| `gh api -X POST/PATCH/DELETE` | ✅ |
| 分支创建 / 删除、保护规则变更 | ✅ |
| Issue / PR 标签变更 | ✅ |

**圆桌中，席位 Agent 的每一次评论都是一次外部写 → 必须进日志。**
**幂等键与日志键一致**：日志条目的 `幂等键` 字段直接填评论头里的那个值。

日志条目字段：

```
时间 | 操作 | 目标（仓库 + issue/PR 号） | 理由 | 执行者（席位） | 幂等键 | 关联 Issue
```

---

## 9. 结束与收尾

会议结束需要三件事，缺一不可：

1. **chair 发布结束评论**：写明结论、遗留分歧、被否决的方案及否决理由；
2. **产出 `docs/ROUNDTABLE_<date>.md`**：摘要 + 链接回 Issue。
   Issue 是完整现场，**不得关闭而不留摘要**；
3. **所有外部写操作已进** `external-write-log.md`。

摘要文件结构：

```markdown
# 圆桌摘要 RT-<YYYYMMDD>-<nn>

- 议题：
- 参与席位 / 模型：
- 轮次：
- 现场：<Issue URL>

## 结论

## 已否决的方案与理由

## 未决分歧

## 后续动作（对应 Issue / 里程碑）
```

## 10. 与里程碑证书制的关系

`AGENTS.md` 要求每个实现任务带 MNN-SNN-GNN 证书（定义在 Controller 侧，**不入库**）。

为了让可追溯性在公开仓库里也成立：

- **证书正文复制进对应 GitHub Issue 作为模板正文**；
- 模板保存在 `docs/templates/MILESTONE_CERTIFICATE.md`。

这样既满足可追溯要求，又在 GitHub **明牌**。

## 11. 权威关系总表

| 内容 | 权威位置 | 其他位置的角色 |
|---|---|---|
| 现状 | `docs/CURRENT_PROJECT_STATE.md` | Controller 侧 = 指针 |
| 架构 | `docs/ARCHITECTURE.md` | Controller 侧 = 指针 |
| **讨论过程** | **GitHub Issue**（公开现场） | 本地 `docs/` = 结论摘要 + 链接 |
| **结论** | `docs/ROUNDTABLE_<date>.md` | Issue = 完整现场（不得关闭而不留摘要） |
| 里程碑批准 | **用户在 Issue 的明确表态** + `stage:approved` | Controller handoff = 指针，不复制全文 |
| 工程批次证据 | `docs/P*_*.md` + tag | — |
| Controller Loop 治理层 | **不入库**（治理层，非项目事实） | 仓库不镜像其内容 |

**核心规则**：Issue = 过程权威；`docs/` = 结论权威；tag = 时间锚点。

## 0. 文档目的、范围与权威边界

### 0.1 文档目的

本规范记录 RPG Progression 模块经过多轮讨论后已经决定的产品哲学、能力成长机制、奖励规则、校准规则、等级规则，以及它与现有 Quest、Task、Gacha、AI 任务生成和 UI 的交互边界。

本规范的目标是让现有系统的其他模块能够依据稳定的产品契约开展衔接设计，避免每次调整 EXP 算法或数据库结构时都重新讨论产品哲学。

### 0.2 系统定位

RPG Progression 是「超级自动化学习工具」现有系统上的重要成长模块，不是一个独立 RPG 学习软件，不另建一套任务管理、任务调度或抽卡系统。

系统总体关系：

- Campaign：长期成长目标。
- Quest：有明确能力目标的成长过程与任务串。
- Task：颗粒度适中、可启动、可执行的行动单元。
- Gacha：从已有可执行任务中选择当前合适的行动，降低启动阻力。
- Assessment：核验用户是否真正证明了目标能力。
- Evidence：记录能力判断所依据的证据。
- RPG Progression：维护能力图谱、能力估值、EXP、等级和校准状态。
- AI：辅助生成任务、考核、能力图谱草案及开放式成果分析；不掌握正式 EXP 结算权。

### 0.3 权威边界

本文件是 **RPG Progression 产品设计的权威来源**，描述目标产品行为。

它不覆盖或替代现有系统的工程事实。实际集成前，主控必须审计当前代码、运行入口、数据库和现有模块，不得仅凭旧架构文档推断实现现状。

### 0.4 本规范不承诺的事项

本规范冻结产品机制，不意味着以下事项已经确定或实现：

- EXP 的完整数学公式、系数、精确权重和等级阈值。
- 证据充分性、证据新鲜度和校准周期的具体算法。
- 行动货币的具体数额、兑换价格和消费场景。
- SQL DDL、数据库索引、API、Python 类、函数及具体事件总线实现。
- 具体 UI 组件、视觉稿和动画。
- 任何 MVP、分期上线或商业化计划。

上述内容属于后续工程设计和实测调优范围，但不得违反本规范的产品规则。

# A. 正式冻结的产品哲学

## A.1 EXP 的唯一诚实性定义

正式 EXP 代表系统基于当前可信证据，对用户在特定能力领域中真实技术能力水平的校准估值。

以下行为只代表行动投入，不自动代表能力掌握：

- 看完网课。
- 阅读教材或文档。
- 记录学习时长。
- 勾选任务完成。
- 浏览知识点。
- 复制或收藏代码。
- 完成一个没有能力验收的输入任务。

这些行为可以获得行动反馈和任务奖励，但不得仅凭其发生就产生正式能力 EXP。

系统的首要目标不是让用户持续看到漂亮的成长数字，而是尽可能减少「系统显示的能力」与「用户实际能做到的能力」之间的虚假差距。

如果用户误以为自己掌握了某项知识，或 AI 错误认可了考核结果，系统必须能够通过后续证据纠正当前能力估值，必要时纠正历史错误授予的成就。

## A.2 行动记录、能力证据与当前能力分离

必须保持三个相互独立的概念：

1. **Action（行动）**：用户过去实际做过什么。属于历史事实，应永久保留。
2. **Evidence（证据）**：用户通过什么成果、考核或表现证明了某项能力。原始证据与其产生时的标准版本应永久保留。
3. **Progression（成长状态）**：系统根据当前有效证据判断用户现在掌握什么。当前状态允许上调、下调和重新校准。

历史上做过一件事，不等于已经证明了能力；历史上证明过能力，也不等于当前仍然保持同等水平。

## A.3 努力与能力双轨正反馈

系统同时提供两条正反馈轨道：

### 行动正反馈轨道

肯定用户完成了合理、具体、可启动的行动。可体现为：

- Task 完成状态。
- Quest 进度推进。
- 连续行动记录。
- 合理的行动货币奖励。
- 执行时长与行动日志。
- 成长面板中的已接触、已探明或行动进展标记。

行动轨道不负责宣称用户已经掌握技术能力。

### 能力正反馈轨道

只有可信证据证明了能力表现，才更新对应 OC、CU、正式 EXP 和掌握认证。

用户完成了任务但没有获得 EXP，不代表任务失败或系统没有奖励；它表示行动已经被肯定，但尚未产生足以证明能力提升的证据。

## A.4 局部诚实估值与核心短板门控分离

任何已经通过验证的具体能力标准（OC），都应如实贡献对应能力估值。

核心标准（Core OC）的作用是决定 CU 是否可以获得完整掌握认证，以及用户是否满足 Domain Level 的核心能力底线。

**Core OC 未达标不得对整个 CU 的 EXP 进行人为严厉封顶。**

例如，用户已经证明一个 CU 的五项标准中的四项，剩余一项核心标准尚未通过：

- 已证明的四项能力仍然贡献相应 EXP。
- 缺失的核心标准清楚显示为短板。
- CU 不得显示为完整掌握（Mastered）。
- 不能通过辅助标准的高分掩盖核心短板并取得高等级认证。

## A.5 校准与复习服务于能力维护，不充当学习门禁

- 时间流逝本身不自动扣减 EXP。
- 长期缺乏直接证据可以使能力进入「待校准」状态。
- 校准任务用于判断能力是否保持、部分生疏或真实退化。
- 复习不是新知识学习的前置条件。
- 用户刚学完新知识时，可以立即开展应用和考核，不必先补做其他知识点的复习。
- 复习与应用可以互相产生证据，但不能强制形成固定先后锁。

## A.6 模块边界与人机主权

- Quest 管成长路线与任务串。
- Task 管具体行动与执行状态。
- Gacha 管从可执行任务中选择行动。
- Assessment 管考核组织与结果核验。
- Evidence 管证据归档与能力映射。
- Progression 管能力状态、EXP、等级和校准。
- AI 负责生成、分析和提出建议。
- 确定性代码负责正式状态流转、奖励结算、EXP 核算和审计。
- 正式能力图谱的创建、拆分、合并和重大修改必须经过用户审核。

任何模块不得因方便而越权替代另一个模块。

# B. 能力图谱与能力单元

## B.1 逻辑四层结构

能力图谱采用四层逻辑组织：

| 层级 | 名称 | 定义与职责 |
|---|---|---|
| 第一层 | Domain | 宏观能力领域，例如 Python 工程能力、数学能力、英语能力 |
| 第二层 | Capability Cluster | 中观能力组织，例如函数抽象与元编程、HTTP 与服务端开发 |
| 第三层 | Capability Unit（CU） | 具有独立价值、可独立验证和诊断的能力单元；正式 EXP 估值单元 |
| 第四层 | Observable Criteria（OC） | 可观测、可考核的具体能力标准；能力证据的最小锚点 |

四层是逻辑组织视图，不是严格的单父级树。

## B.2 全局唯一 CU 与跨领域引用

1. CU 在用户的全局能力库中拥有全局唯一且稳定的身份标识。
2. 同一个 CU 可以被多个 Cluster、Quest 和 Domain 引用。
3. Domain 和 Cluster 是能力组织与展示视图，不拥有 CU 的排他所有权。
4. 同一个 CU 及其底层语义完全相同的 OC，其有效证据在全局能力库中唯一存储、跨引用复用。
5. 不同能力标准不得仅因名称相似而自动共享证据。
6. 每个 Domain 的 EXP 是其引用 CU 估值的领域统计投影。多个 Domain 可以展示同一 CU 的估值，但不得把各 Domain 投影简单相加并冒充用户的全局独立能力总分。

全局唯一身份意味着能力属于用户，而不属于某条 Quest 或某个 Campaign；它不意味着所有相似场景都自动共享证据。

## B.3 CU 的五项准入标尺

一个能力只有同时具备以下五项属性，才适合成为独立 CU 并持有正式 EXP：

1. **独立应用价值**：这项能力本身具有可识别的使用价值，而不只是一个孤立术语或语法碎片。
2. **跨 Quest 复用潜力**：不同成长路线可能再次调用这项能力。
3. **独立验收闭环**：能够设计相对独立的考核，判断用户是否具备该能力。
4. **独立诊断与补救闭环**：能够识别这项能力的具体短板，并据此设计有针对性的补强任务。
5. **正交职责边界**：与相邻能力之间存在足够清晰的边界，避免重复估值或职责重叠。

切分原则：

- 过细的知识点、语法点和局部表现通常归入 OC。
- 过于庞大、包含多个独立应用能力的集合通常归入 Cluster。
- CU 不应为了制造更多 EXP 而无限拆细。
- CU 不应粗到无法识别具体短板。

考核时间长度不是 CU 的硬性准入条件；不同学科和能力的合理验收成本可以不同。

## B.4 渐进式按需生长（Just-in-Time Graph）

1. Campaign 创建时确定所属 Domain、成长目标与初步能力范围，不要求一次性穷举所有远期能力。
2. 远期尚未展开的能力允许处于「战争迷雾」中。
3. 具体 Quest 展开时，优先检索和复用全局能力库中已有的 CU。
4. 确实不存在合适 CU 时，AI 或规划者才提出新 CU 草案。
5. 当前 Quest 正式开始执行前，其关联 CU 下的 OC 和验收标准必须明确。
6. 正式能力节点的创建、拆分、合并和重大修改必须经过用户审核。
7. 已经产生证据的标准不得被静默改写；变更必须保留版本和迁移记录。

## B.5 拆分守恒、新能力扩容与迁移

### 已有 CU 拆分

将已有粗粒度 CU 拆分为多个子 CU 时：

- 子单元的基准权重总和继承原单元权重，不能仅因拆分而凭空增加原有能力预算。
- 拆分必须说明旧 OC 与新 OC 的对应关系。
- 拆分不得静默改变用户已经积累的历史能力估值。

### 新能力扩容

引入真正不同、具有独立应用价值的新能力时，允许能力图谱总容量自然增长。

不采用一个固定、不可扩展的 Cluster 总预算来阻止真实新能力进入图谱。需要守恒的是既有能力拆分造成的纯结构性变化，而不是禁止能力领域成长。

### 历史证据迁移铁律

- 原 OC 能明确对应新 OC：允许迁移其实际覆盖的历史证据。
- 原 OC 仅部分支持新 OC：只能继承对应部分。
- 原 OC 无法对应新 OC：标记为待重新验证，不得推断已经掌握。
- 原始 Evidence 永久保留产生时的 OC、Rubric 和图谱版本快照。
- 图谱调整及其对 EXP、掌握状态和等级的影响必须在成长日志中透明展示。
- 全局 CU 被拆分时，必须检查所有引用该 CU 的 Domain 和 Cluster；不得只修改一个领域的视图，却静默改变其他领域的含义。

# C. 能力画像与证据体系

## C.1 受控通用维度池与领域选配

系统维护受控的通用能力表现维度池。当前建议维度包括：

- 概念理解。
- 主动提取。
- 独立构建。
- 调试与修改。
- 问题分析。
- 陌生场景迁移。

不同领域、不同 CU 可以按自身性质选配相关维度，定义自己的 OC 和验收标准。

不强迫所有学科使用完全相同的六维画像，也不允许完全任意定制到失去可解释性。通用维度池提供共同语言，领域 Rubric 负责具体化。

## C.2 能力表现与证据质量分离

必须区分：

- **能力表现维度**：用户实际展示了什么能力。
- **证据质量属性**：这份证据有多可靠、覆盖了多少、是否足以支持该能力判断。

证据质量至少应能表达以下信息：

- 独立性与外部辅助程度。
- 评估可靠性。
- 难度与目标能力的匹配程度。
- 实际覆盖的能力范围。
- 新颖性与重复程度。
- 场景与时间信息。
- 用户实际参与的操作类型。

证据质量属性不等于能力维度，不应把两者混为一个统一等级。

还必须区分以下四个相互关联但不能互相替代的判断：

- **能力估值**：当前有效证据支持用户达到什么能力水平。
- **证据充分性 / 可靠程度**：现有证据是否足以支持当前判断。
- **证据新鲜度**：现有证据距离当前有多久、是否需要重新校准。
- **证据覆盖度**：CU 下哪些 OC 已经被验证，哪些仍然缺失。

证据充分性、可靠程度、新鲜度和覆盖度不是 EXP，也不应被压缩成一个未经校准的伪精确数字。它们用于解释估值的可靠边界、是否需要复测以及具体缺口。

同构重复题不能线性增加证据充分性；高度相似的多次练习不等于多份独立证据。证据多样性、独立性、跨时间表现和跨场景表现更有意义。

## C.3 工具与 AI 辅助的证据质量准则

证据质量不取决于用户是否使用工具，而取决于工具是否替代了当前 OC 要检验的核心能力。

### 不应自动扣分的正常工具

- 查阅官方文档。
- 使用 IDE 常规补全。
- 使用调试器。
- 使用正常开发环境中的搜索和参考资料。

### 底层实现类 OC

如果当前 OC 要验证用户能否独立构建某项底层能力：

- AI 生成核心代码后，用户只会运行或解释结果，不能证明从零独立构建能力。
- 用户通过白盒解释、修改和微变体盲改，可以证明相应的审查、理解、调试或修改能力。
- 这些表现应按各自 OC 分别判断，不能把「会审查 AI 代码」自动等同于「能从零独立实现」。

### AI 辅助工程类 OC

如果当前 OC 本身就是验证用户能否利用 AI 完成工程工作：

- 准确引导 AI。
- 审查生成结果。
- 识别错误。
- 独立验证。
- 必要时修改和整合。

这些行为本身就是目标能力，可以作为有效乃至完整的证据。

**禁止采用对所有 AI 辅助行为统一扣除固定比例的规则。** 必须根据当前 CU 和 OC 的目标能力判断。

## C.4 一份证据映射多个能力（M:N）

一份综合项目证据可以映射到多个 CU 下的多个 OC，但必须满足：

1. 每个映射都能指出该证据中的具体操作、产物或答辩内容。
2. 每个 CU 只获得其名下实际被主动构建、展示并独立验收通过的 OC 证据。
3. 不得因为 Task 或 Quest 声明依赖某个 CU，就自动认为用户证明了该 CU。
4. 纯黑盒调用第三方库或现成封装函数，对其底层实现节点不产生证据贡献。
5. 如果用户只是调用了封装能力，可以证明正确使用该接口的能力，但不能据此证明封装内部算法的实现能力。
6. 同一份 Evidence 可以支持多个不同 CU，但同一个 OC 的同一份证据不得在不同 Quest 中重复发放 EXP。

证据映射应当能够区分用户在项目中的参与方式，例如主动编写、主动调试、审查修改、黑盒调用等。不同 OC 的独立性与辅助情况可以不同，不能只用一个整项目分数掩盖局部差异。

## C.5 下游任务证据与上游能力刷新

任务依赖关系不等于能力证据。

下游任务只有在用户实际参与了上游能力对应的操作，并且该操作满足目标 OC 的验收要求时，才可以刷新相应能力证据。

例如，完成 FastAPI 鉴权任务：

- 用户主动实现并调试装饰器，可以为装饰器相关 OC 提供证据。
- 用户复制旧代码或调用别人封装好的鉴权装饰器，不自动刷新装饰器实现能力。
- 只使用某项能力的结果，不等于重新证明了该能力。

# D. 双轨正反馈与行动货币

## D.1 双轨反馈职责

### 行动轨道

合规完成 Task 后，系统记录行动完成状态、Quest 进度、行动日志，并按规则给予行动货币。

行动轨道可以将相关能力点标记为已接触或已探明，但这种标记只是行动与接触记录，不是能力通过证明，也不自动产生 EXP。

### 能力轨道

只有 Assessment 产生有效证据，并通过对应 OC 的验收，才更新能力状态和正式 EXP。

Task 完成与能力掌握不是同一事件。

## D.2 行动货币六条反通胀规则

1. **锚定真实工作量**：奖励依据合理预计工作量与认知负荷核定，不按 Task 数量简单计件。
2. **单实例唯一结算**：同一个 Task 实例无论经历何种状态流转，其完成奖励只能领取一次。
3. **拆卡预算守恒**：纯粹将一个大 Task 拆成多个子 Task 时，子任务行动货币总预算继承原任务预算，不能靠拆碎任务凭空创造额外奖励。
4. **考核失利零追回**：后续考核未通过或 EXP 下调，不追回此前诚实完成任务获得的行动货币。
5. **重测防刷机制**：因考核失败派生的重测卡不再重复发放行动货币；投入新学习、练习和编码工时的补强训练卡，按正常工作量发放行动货币。
6. **异常审计纠错**：系统异常或误操作造成重复入账时，通过可追溯的奖励流水执行幂等纠错，不直接抹除历史流水。

## D.3 独立考核卡的有效尝试门槛

独立考核卡包括 Capstone、Level Boss、定期校准卡等。

必须同时遵守以下规则：

1. 同一考核目标只允许领取一次首次有效尝试的行动奖励。
2. 首次有效尝试必须包含符合考核要求的实质性提交；交白卷、无关提交、秒退或仅打开卡片不构成有效尝试，不发放行动货币。
3. 首次有效尝试无论通过还是失败，都可以按规则领取一次行动奖励。
4. 因失败而重新生成的同目标考核卡、同构变体复测卡和 Re-test Card，不再重复发放行动货币。
5. 补强训练卡属于新的学习与构建行动，按实际工作量正常发放行动货币。
6. 无效尝试可以留下审计记录，但不能被当作有效能力证据，也不能冒充有效失败考核。
7. 独立考核卡完成实质性提交后，即使考核未通过，该 Task 实例也必须立即结束并归档，不得永久滞留在待办池中。

「同一 Task 实例只能结算一次」与「同一考核目标只能领取一次首次有效尝试奖励」是两条不同规则，必须同时实现。

## D.4 奖励与能力下调的关系

- 考核失败不追回已获得的行动货币。
- 真实遗忘导致 Current EXP 下调，不影响过去诚实完成任务获得的行动货币。
- 只有被证明是系统重复入账、欺诈或错误结算的奖励，才按审计规则纠错。
- 不得因为用户当前能力下降，就否定过去确实完成过的学习和训练行动。

# E. Task、Assessment 与 Capability 三态隔离

三者必须是独立状态维度，不得合并成一个「完成/未完成」字段。

| 维度 | 核心问题 | 典型状态 | 说明 |
|---|---|---|---|
| Task | 用户是否做完了这件具体的事？ | 未解锁、可抽取、已破冰、已完成 | 记录行动与任务实例生命周期 |
| Assessment | 本次能力检验是否通过？ | 未触发、核验中、通过、未通过 | 记录一次具体测试或答辩的结果 |
| Capability | 用户当前是否掌握这项能力？ | 未接触、已探明、部分证明、完整掌握、待校准、已退化 | 根据 CU 下各 OC 当前有效证据综合决定 |

「已接触/已探明」可以由行动轨道点亮，但不代表 OC 已通过。

## E.1 普通练习与应用任务

- 可以内嵌轻量自动化检查。
- 通过时：Task 完成，Assessment 通过，生成对应 OC 的证据并更新能力。
- 未通过时：只要用户按要求完成了实际练习或提交，Task 仍可完成并获得行动奖励；Assessment 记录未通过；Capability 不因此变为掌握。
- 系统根据暴露的盲区生成补强任务。
- 用户不需要因为一次失败而重复领取原任务的行动奖励。

## E.2 独立高阶考核卡

- 用于白盒追问、微变体盲改、开放式评审、Capstone、Level Boss 或定期校准。
- 用户完成实质性提交后，本次考核卡实例结束并归档。
- Assessment 记录通过或未通过及其诊断结果。
- 未通过时触发补强训练或重测流程。
- 失败的原卡不重新进入待办池。
- 重测卡不发重复行动货币；补强训练卡正常奖励。
- 空白或无效提交不构成有效尝试，不产生能力证据，也不领取首次考核行动奖励。

# F. EXP 估值、掌握认证与校准

## F.1 EXP 的存量估值原则

正式 EXP 是当前能力估值，而不是行为事件的简单累加。

- 每个 CU 是正式 EXP 估值单元。
- OC 是能力证据的最小锚点。
- 已验证 OC 按其能力贡献与证据质量进入 CU 估值。
- 同一 OC 的重复验证用于更新或增强当前判断，不得反复累计同一份能力价值。
- EXP 更新采用存量估值变化的差额结算思想：只结算新旧能力估值之间的变化。
- 具体公式、权重、系数和归一化方式留待工程阶段确定。

## F.2 Core OC 与 Mastered 认证

每个 CU 可以定义核心标准（Core OC）与辅助标准。

- 任意已验证 OC 都可以贡献 EXP。
- 任意 Core OC 未达标时，CU 不能获得完整掌握（Mastered）认证。
- 未达标的核心标准必须作为显式短板展示。
- 辅助标准的高分不能掩盖核心短板。
- Core OC 不对整个 CU 的 EXP 进行严厉封顶。
- Domain Level 晋升时，必须检查该等级要求的核心 CU 是否全部获得完整掌握认证。

CU 的 EXP 数值和 Mastered 状态是两个相关但不同的表达。

## F.3 Current EXP 与 Peak EXP

- **Current EXP**：当前有效证据支持的能力估值。
- **Peak EXP**：历史上曾经由真实、有效、未被证伪的能力证据支持过的最高估值。
- 历史行动与原始证据永久保留。
- 真实遗忘可以降低 Current EXP，但不抹除真实达到过的 Peak EXP。
- 如果证明过去的考核本身严重无效，则相关证据被追加标记为已证伪，Current EXP 与 Peak EXP 均应按有效历史重新计算。
- 如果历史 Level 认证依赖的核心证据被证伪，也必须按有效历史重新计算 Peak Level；曾经授予及后来撤销的等级记录仍永久保留，并显示撤销原因。
- 不得为了用户粘性而保留已经证明虚假的 Peak EXP 或 Peak Level。

## F.4 证据新鲜度与校准

- 时间流逝不直接扣 EXP。
- 长期缺少直接练习、下游主动构建或其他有效证据时，可以将能力标记为待校准。
- Progression 可以向任务系统提供校准需求，由 Quest 组织校准任务，Gacha 将已解锁的校准任务作为普通候选任务。
- 校准任务不构成新知识学习的前置锁。
- 只有实际验证结果才能改变 Current EXP。

## F.5 四类校准归因

| 归因 | 判定逻辑 | 当前能力处理 | 历史成就处理 |
|---|---|---|---|
| 偶然失误（Slip） | 初测失败，但同构变体复测成功 | 不下调 EXP，解除待校准 | 保留 |
| 真实遗忘（Forgetting） | 曾有高可信证据，之后多次独立复测失败 | 按失败 OC 的实际表现下调 Current EXP | 保留真实 Peak EXP |
| 历史评估虚高（Overestimate） | 证明原始考核严重失效或当时证据不足以支持原结论 | 下调 Current EXP | 证伪相关历史证据，并回溯修正 Peak EXP |
| 重新证明（Revalidation） | 新项目、恢复练习或新考核重新通过对应 OC | 恢复或提高 Current EXP | 更新真实历史峰值（如有） |

一次失败不能自动推断过去是误判还是后来遗忘。

无法确定时，应保留不确定性并继续收集证据，不得武断改写历史。

## F.6 证据不可变与纠错事件

- 原始 Evidence 作为历史事实不可覆盖、不可删除。
- 对证据有效性、适用范围和历史估值的后续判断，通过追加裁决、纠错或迁移事件表达。
- 原始证据与后续裁决必须同时可追溯。
- 不得通过静默修改旧证据字段来实现历史纠错。

# G. Domain Level、Synthesis CU 与初始定级

## G.1 Domain Level 的职责

Domain Level 是用户在某个能力领域的综合能力阶段认证，不是 Task 完成数量，也不是学习时长的累计。

展示至少区分：

- Current Level：当前证据支持的等级。
- Peak Level：历史上真实达到过的最高等级。
- 待修复/能力受损预警：当前能力证据不足以继续支持原等级时的状态提示。

## G.2 Domain Level 晋升条件

晋升同时检查：

1. 领域总 EXP 达到相应阈值。
2. 本等级要求的核心 CU 全部获得完整掌握认证。
3. 如果该 Domain 定义了高阶综合能力要求，则必须通过相应综合能力验证。

具体阈值与核心 CU 清单由领域设计定义，具体数值留待后续确定。

## G.3 等级与任务准入解耦

- Domain Level 不得作为阻断用户开启高阶 Quest 的一刀切门禁。
- 具体 Quest / Task 是否可以执行，由实际 DAG 前置依赖和明确的能力要求决定。
- 如果用户存在能力缺口，系统应给出风险提示和前置补课建议。
- 用户保留跨级探索和主动挑战的自由。
- 等级是能力认证与成长反馈，不是行政式任务权限系统。

## G.4 Synthesis CU（综合能力单元）

Synthesis CU 是一种能力单元类型，用于表达多个底层能力组合后产生的、具有独立价值的高阶能力，例如：

- 跨模块组合。
- 系统级权衡。
- 复杂迁移。
- 多模块接口契约设计。
- 故障传播、隔离与恢复。
- 综合建模、复杂证明或跨语境表达。

规则：

1. Synthesis CU 与普通 CU 一样，必须有独立 OC 和有效证据。
2. 通过 COMPOSES_INTO 等关系关联底层基础 CU。
3. 只能奖励底层 CU 无法表达的新增综合能力。
4. 不能仅仅因为一个项目调用了多个基础模块，就自动获得综合能力 EXP。
5. 一份综合项目可以同时证明底层 CU 和 Synthesis CU，但每个节点都必须有独立的证据依据。
6. 不同 Domain 根据学科特点决定是否需要 Synthesis CU，以及需要何种综合能力。
7. 不强制所有学科、所有等级拥有相同数量或相同形式的综合节点。

## G.5 初始能力探测与跳级（Onboarding & Skipping）

新用户或新 Campaign 不应默认所有能力均为零。

支持：

- 分级挑战。
- 既有项目成果白盒审查。
- 同构变体测试。
- 对已有能力直接提交证据。
- 通过可靠验证后直接建立相应 CU 的初始估值与掌握状态。
- 复用全局能力库中已经证明的 CU，避免重复学习。

初始定级与日常学习采用相同的证据标准，不因为是入场测试就降低验收要求。

已经证明的能力应当豁免对应的基础学习任务。对于部分证明的 CU，任务设计应尊重已通过的能力标准，不应要求用户机械重学已经证明的内容；尚未证明的标准仍可安排相应学习和考核。

# H. 与现有系统的跨模块交互契约

## H.1 Quest / Task 管理

### Quest 职责

- 规划 Campaign 内的成长路线。
- 组织 Quest 与 Task。
- 声明希望培养、验证或巩固哪些 CU / OC。
- 根据 Progression 提供的能力缺口设计补课支线。
- 根据能力状态调整后续任务难度和内容。

### Task 职责

- 表达具体、可启动的行动。
- 记录行动执行状态。
- 可以声明输入、练习、应用、交付或考核类型。
- 可以关联一个或多个 CU / OC。
- 综合 Task 可以关联多个能力目标。
- Task 完成不自动意味着能力通过。

### 禁止事项

Quest / Task 管理不得自行宣布用户掌握能力，也不得直接发放正式 EXP。

## H.2 Gacha 抽卡引擎

Gacha 的核心职责继续保持为：从现有可执行任务中，依据系统已有的时间、精力、阻力、连携等规则，选择当前合适的行动，降低启动阻力。

- 校准卡可以成为普通候选任务。
- 补强训练卡可以成为普通候选任务。
- Gacha 不负责能力估值。
- Gacha 不负责能力图谱创建、拆分或修改。
- Gacha 不负责重新规划整个 Quest。
- 能力缺口可以影响 Quest 的任务设计和候选任务准备，但不能让 Gacha 变成另一个复杂学习规划器。
- 已启动任务保护、点火动作和用户返回全局池的能力继续遵循现有 Gacha 产品规则。

## H.3 Assessment 核验引擎

职责：

- 根据目标 OC 和 Rubric 组织自动化检查、白盒追问、微变体盲改和开放式评审。
- 记录每次考核尝试。
- 对每个 OC 输出结构化核验结论。
- 记录独立性、辅助情况、覆盖范围、难度匹配和评估可靠性等证据属性。
- 生成不可变 Evidence。
- 允许一次 Evidence 映射多个 OC / CU。

禁止直接修改 EXP、等级或任务树。

## H.4 AI 任务与考核生成

AI 可以：

- 根据 Campaign 目标提出能力图谱草案。
- 检索并复用已有 CU / OC。
- 在确有需要时提出新 CU 草案。
- 为已有 CU / OC 生成 Quest、Task 和考核。
- 分析代码、项目、答辩和开放式答案。
- 识别能力缺口。
- 提出补强任务、校准任务和图谱迁移建议。

AI 不可以：

- 直接输出并结算正式 EXP。
- 未经审核创建、拆分、合并或重写正式能力节点。
- 修改原始历史证据。
- 仅凭 Task 完成认定能力掌握。
- 仅凭 DAG 依赖关系刷新上游能力。
- 未经用户审核覆盖已启动任务或正式任务结构。

## H.5 RPG Progression

职责：

- 维护全局能力图谱与版本。
- 维护 CU / OC 的定义、引用和状态。
- 接收 Assessment 产生的 Evidence。
- 管理 Evidence 与 OC / CU 的映射。
- 计算 Current EXP 与 Peak EXP。
- 判定 CU 掌握状态。
- 判定 Domain Level 与核心能力底线。
- 识别待校准能力。
- 输出能力缺口和成长历史。
- 提供 EXP 变化溯源。

禁止：

- 接管 Quest 的路线与任务编排。
- 接管 Gacha 的实时抽卡与选择算法。
- 因 Task 完成直接产生 EXP。
- 允许 AI 直接修改正式能力状态或 EXP。

## H.6 成长面板与 UI

UI 应分别展示行动反馈和能力反馈：

- 行动完成、Quest 推进、行动货币和行动历史。
- 当前 EXP、Peak EXP、Current Level、Peak Level。
- CU 的部分证明或完整掌握状态。
- 未通过的 Core OC 与具体能力短板。
- 待校准提示。
- 能力证据和 EXP 变动溯源。
- 已豁免的基础任务与尚未证明的能力。

用户完成输入任务但没有 EXP 时，UI 应明确显示任务已完成及行动奖励，不得渲染为失败。

UI 不得展示没有证据来源的黑箱分数变化。

# I. 端到端事件闭环

典型闭环如下：

1. Quest 根据 Campaign 目标声明希望培养的 CU / OC。
2. Task 管理建立具体、可执行的 Task。
3. Gacha 从已解锁、可执行的 Task 中抽取一个行动。
4. 用户执行 Task，系统记录 Action Event。
5. Task 根据行动要求结束并记录完成状态。
6. 如果任务有验收要求，触发 Assessment。
7. Assessment 根据 Rubric 执行自动化测试、白盒追问或开放式评审。
8. Assessment 记录 PASS / FAIL、尝试有效性和证据质量。
9. 有效证据进入 Evidence Manager。
10. Evidence 映射到实际被证明的 OC；一份证据可以映射多个 OC。
11. Progression 根据当前有效证据更新 OC / CU 状态、Current EXP、Peak EXP 和 Domain Level。
12. 失败、短板或待校准状态形成结构化能力缺口。
13. Quest 消费能力缺口，决定是否生成补强支线或后续任务。
14. Gacha 继续从已准备好的任务中选择行动。
15. UI 分别展示行动正反馈与能力成长反馈。

必须满足：

- Task COMPLETED 与 Assessment PASS 是两个独立事实。
- Assessment FAIL 不删除 Action Event。
- 一次考核不能被重复结算。
- 一份证据可以支持多个节点，但每个 OC 必须有独立依据。
- EXP 变化必须能追溯到证据和对应标准版本。
- 失败考核也必须留档。
- 同一个 OC 的相同能力价值不能在多个 Quest 中重复发放。
- EXP 和行动货币的结算都必须具有幂等性。
- 相关状态更新应保持一致，不能出现任务已结算但能力状态或奖励流水部分缺失的情况。

# J. 概念数据关系（非 SQL 设计）

以下是产品层必须表达的概念关系，不要求每个概念最终都独立成为数据库表。

| 概念实体 | 产品职责 |
|---|---|
| Capability Domain | 领域视图与等级体系 |
| Capability Cluster | 领域内能力组织 |
| Capability Unit | 全局唯一的能力估值单元 |
| Observable Criteria | CU 下具体可验证的能力标准 |
| Graph / Domain / Cluster / CU / OC / Rubric Revision | 记录领域引用、能力节点、可观测标准和 Rubric 的历史版本及其生效边界 |
| Task Capability Mapping | 一个 Task 对应一个或多个 CU / OC |
| Action Event | 用户真实执行行动的历史事件 |
| Assessment Session / Attempt | 一次考核及其尝试、结果和有效性 |
| Evidence | 不可变的原始能力证据 |
| Evidence OC Mapping | 一份证据支持哪些 OC，以及具体覆盖和参与情况 |
| Capability State | 当前 OC / CU 的掌握状态 |
| EXP Calibration Event | 能力估值上调、下调、纠错和重新校准的溯源事件 |
| Level Snapshot | 当前等级与历史等级变化 |
| Reward Ledger | 行动货币奖励、重测限制与异常纠错流水 |
| Graph Migration Mapping | 节点拆分、合并及历史证据迁移关系 |

关键关系：

- 一个 Task 可以关联多个 CU / OC。
- 一个 Evidence 可以映射多个 OC。
- 一个 OC 可以拥有多份历史 Evidence。
- 一个 CU 可以被多个 Domain / Cluster 引用。
- 一个 Domain 可以引用多个 CU。
- 一个 Assessment Attempt 可以失败，但仍然留有完整记录。
- 当前能力状态可以依据历史证据与后续裁决重建。
- 原始 Evidence 不可变；后续有效性判断通过追加事件表达。

# K. AI 与确定性代码的职责契约

## K.1 AI 负责

- 能力图谱草案。
- Quest / Task 草案。
- Assessment 题目与 Rubric 草案。
- 开放式答案、代码和项目成果分析。
- OC 级证据映射建议。
- 能力缺口识别。
- 补强、迁移和校准任务建议。

## K.2 确定性代码负责

- 正式能力图谱版本与状态管理。
- 用户审核结果的应用。
- Evidence 入库与不可变性。
- Evidence 到 OC 的映射关系校验。
- EXP 存量估值与差额结算。
- Mastered 判定。
- Domain Level 判定。
- 行动货币唯一结算、同目标限领与幂等纠错。
- 历史审计、证据裁决与重算。

## K.3 人类用户的审核权

正式 CU 的创建、拆分、合并、重大 OC 变更、图谱迁移和影响既有能力估值的操作，必须经过用户审核。

AI 的评估结果是结构化证据建议，不是正式 EXP 指令。

# L. 产品验收场景

以下场景用于验证产品规则是否自洽，不代表具体测试代码或公式已经实现。

## L.1 看完课程但没有证明能力

用户看完「Python 函数」网课：

- Task 完成。
- 行动日志与行动奖励正常结算。
- 相关知识点可以标记为已接触。
- 没有足够能力证据，因此不产生正式 EXP。
- UI 明确表达行动已完成，而不是任务失败。

## L.2 普通练习考核失败

用户完成装饰器练习并提交，但自动检查失败：

- Task 仍可完成。
- Assessment 记录未通过。
- 该失败暴露能力短板，但不证明用户已经掌握。
- 用户按实际练习行动获得正常行动奖励。
- Quest 可以生成补强训练。

## L.3 独立考核卡首次失败

用户完成 Capstone 的实质性提交，但未通过：

- 该考核卡实例立即 COMPLETED 并归档。
- Assessment 记录 FAIL 与诊断。
- 首次有效尝试可以领取一次行动奖励。
- 系统生成补强训练卡或 Re-test Card。
- Re-test Card 不重复发行动货币。
- 补强训练卡按真实工作量正常奖励。

## L.4 空白提交或秒退

用户打开独立考核卡后没有提交实质性成果：

- 记录无效尝试或退出事实。
- 不发放首次考核行动奖励。
- 不产生能力 Evidence。
- 不得将其伪装为有效 FAIL 或有效 PASS。

## L.5 Core OC 未通过，但其他 OC 已证明

用户已经证明 CU 的多数辅助标准，但某项核心标准失败：

- 已证明的 OC 仍然贡献 EXP。
- CU 显示部分证明与核心短板。
- 不授予 Mastered。
- 不满足依赖该 Mastered 状态的 Domain Level 核心底线。

## L.6 AI 辅助开发

用户使用 AI 生成一部分代码：

- 对独立构建类 OC，不能仅凭代码运行成功就认定从零构建能力。
- 用户能够解释、修改和盲改，可以证明相应审查、理解、调试或修改能力。
- 对 AI 工程编排类 OC，正确引导 AI、审查结果并独立验证本身就是目标能力。

## L.7 综合项目证明多个 CU

用户独立完成 FastAPI + Pydantic + Agent 项目：

- 项目中主动编写的装饰器可以支持装饰器相关 OC。
- 主动设计的数据校验可以支持 Pydantic 相关 OC。
- 仅调用第三方库不证明其内部算法实现。
- 独立完成工具调用编排、状态管理和系统级异常恢复，可以支持对应 Synthesis CU。
- 底层能力与综合能力分别验收，不重复计算同一项能力价值。

## L.8 下游任务并不自动刷新上游能力

用户完成 FastAPI 鉴权任务：

- 主动实现并调试装饰器，可以成为装饰器能力的新证据。
- 复制代码或调用封装，不自动刷新装饰器实现能力。
- DAG 依赖关系本身不构成证据。

## L.9 真实遗忘

用户曾经高可信地证明装饰器能力，长期未使用后多次独立复测失败：

- Current EXP 按失败 OC 下调。
- Peak EXP 保留。
- 历史证据和历史成就保留。
- 系统生成恢复练习。
- 新项目重新通过后恢复 Current EXP。

## L.10 历史考核虚高

后续证明当初考核过于简单、代写或评估错误：

- 追加历史证据失效裁决。
- Current EXP 按有效证据重算。
- Peak EXP 回溯修正。
- 原始证据和曾经授予的历史记录仍然保留，标记纠错原因。

## L.11 跨 Quest 与跨 Domain 复用

用户在 Python Quest 中证明 Git 基础能力，之后进入 Agent 或前端 Quest：

- 相同 CU / OC 可以复用。
- 不重复发放相同能力的 EXP。
- 不同的 Git 能力标准不能因名称相似自动继承。

## L.12 初始定级与跳过

新用户通过既有项目白盒审查证明了部分 Python 能力：

- 对应 OC / CU 建立初始能力状态。
- 已证明的基础任务豁免。
- 未证明的标准仍然可以生成学习和实践任务。
- 后续 Campaign 复用全局能力证据。

## L.13 行动货币防通胀

用户将一个大任务拆为多个小任务：

- 如果只是任务拆分，子任务奖励预算继承原任务预算。
- 同一实例不能重复领取。
- 同一考核目标的重测不能反复领取行动货币。
- 新增的真实补强训练可以按工作量正常奖励。

## L.14 等级不限制探索

用户当前为 Python Lv.3，但尚未掌握某项 Lv.4 常见能力：

- 可以尝试不依赖该能力的高阶 Quest。
- 依赖该能力的 Task 可以提示风险或建议补课。
- 不以 Domain Level 作为一刀切权限门禁。

# M. 正式冻结与实现弹性清单

## M.1 必须遵守的冻结规则

- EXP 只由可信能力证据支持，不由学习时长或任务勾选直接产生。
- Action、Evidence、Progression 分离。
- 行动与能力双轨反馈。
- 四层逻辑能力图谱。
- CU 全局唯一、跨领域引用。
- CU 五项准入标准。
- 渐进式按需生长。
- 拆分守恒，真实新能力允许扩容。
- OC 级证据映射与多对多关系。
- 能力表现与证据质量分离。
- 工具使用与 AI 辅助按目标 OC 判断。
- 综合能力拥有独立 Synthesis CU，但不重复计分。
- 行动货币工作量锚定、单实例唯一、拆卡预算守恒。
- 独立考核首次有效尝试奖励门槛、同目标限领、重测卡零重复奖励。
- Task、Assessment、Capability 三态隔离。
- Core OC 限制 Mastered 与等级认证，不封顶整个 CU EXP。
- Current EXP 与 Peak EXP 分离。
- 时间不直接扣 EXP，校准基于证据。
- 真实遗忘与历史误判分离。
- 初始定级使用与日常一致的证据标准。
- Domain Level 不作为一刀切任务门禁。
- Quest、Gacha、Assessment、Progression 和 AI 职责分离。
- AI 不直接结算正式 EXP。

## M.2 后续可调整的实现参数

在不改变上述产品含义的前提下，后续可调整：

- CU 基准 EXP 权重档位。
- OC 权重和证据质量计算参数。
- Domain Level EXP 阈值。
- 行动货币发放数额与外围消费场景。
- 证据新鲜度算法与校准周期。
- 各领域对通用能力维度的选配与权重。
- AI 辅助参与度的检测手段。
- Assessment 自动化程度与人工复核方式。
- 数据表、API、服务类、事件流技术实现。
- UI 布局、组件、动画和可视化形式。

任何参数调整都不得破坏冻结的产品语义。

## M.3 不属于本规范的工作

- MVP 设计。
- 独立产品商业规划。
- 上线时间表。
- 具体 EXP 数学模型的最终拟合。
- SQL DDL 与索引。
- API 和前后端代码实现。
- 具体自动化测试框架。
- 当前代码是否已经具备相应功能的判断。

这些工作在后续工程衔接阶段开展。

## M.4 明确不采用的旧方案（防止后续设计回退）

以下方案已经在产品讨论中被否定，不应在后续实现或新一轮设计中无理由复活：

- 学习输入、看课时长、阅读数量或任务勾选直接累计正式 EXP。
- 将输入、应用、复习设计为三条互相竞争的并列 EXP 货币条。
- 复习任务成为新知识应用或新知识考核的前置锁。
- 知识点经过固定天数就自动扣减 EXP；时间只触发校准需求，不直接证明能力消失。
- Core OC 未通过就对整个 CU 的 EXP 严厉封顶。
- 用一条统一的线性证据阶梯强制排列所有学科和能力表现，并把未经验证的固定系数当成能力真值。
- 通过大量相似练习线性增加证据置信度，或仅靠刷重复题换取更长免考周期。
- 仅凭 Task DAG 依赖关系或下游任务完成就自动刷新上游能力证据。
- 将所有迁移应用统一视为原能力固定比例的额外 EXP 奖励。
- 对所有 AI 辅助行为采用统一独立性扣分系数。
- 用历史最高证据的简单最大值直接代表当前能力，从而让后续失败永远无法下调能力估值。
- 让 AI 直接修改正式 EXP、掌握状态或历史证据。
- 让 Domain Level 成为开启高阶任务的一刀切权限门禁。
- 通过拆碎 Task 数量来创造额外行动货币，或让同一考核目标的反复重测无限刷币。
- 为 RPG 单独重建 Quest、Task 或 Gacha，或让 Gacha 接管复杂能力规划。

# N. 与现有系统衔接时的执行原则

1. 本规范是产品目标，不是当前代码实现现状的证明。
2. 主控应先审计现有仓库的真实运行入口、Quest / Task 数据结构、Gacha 行为、AI 任务生成方式、数据库和 UI。
3. 不得为了实现 Progression 重复开发现有系统已经拥有的任务管理、抽卡和行动记录能力。
4. 应先建立现有模块与本规范的映射、差距和数据契约，再提出工程改造方案。
5. 保持模块化单体方向，不为概念上的模块独立而过早引入独立服务。
6. 依赖关系明确的工程工作以主控划分的完整批次线性推进，避免多个 Controller 同时修改同一依赖链。
7. 每个工程批次必须留下可交接的工作痕迹、修改范围、验证证据和剩余问题。
8. 未经单独授权，不修改用户真实知识库、生产 SQLite 数据和运行配置。
9. 任何声称「已经实现」或「已经验收」的功能，必须以当前源码和实际运行证据为依据，不能把本规范中的目标行为写成既成事实。

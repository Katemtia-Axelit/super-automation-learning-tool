## System Purpose

**超级自动化学习工具** is not a Todo list and not a Pomodoro timer. It is a
**closed-loop learning system** where AI is an *assistive* layer, not the
decision authority.

The core loop:

```text
plan
  → task pool
    → intelligent / gacha selection
      → execute
        → timer
          → feedback
            → state
              → knowledge accumulation
```

Read that as a cycle, not a funnel. Execution feeds state assessment (energy,
daily tone, sleep); state feeds the next selection; completed work becomes
knowledge notes in an Obsidian vault; the vault feeds back into planning.

Two design commitments follow, and they explain most of the code:

1. **Selection is weighted, not arbitrary.** A gacha draw scores candidate tasks
   by energy cost, resistance, rarity, priority, and recent-draw state. This is
   why `server/services/gacha.py` is the one piece of business logic that was
   migrated early and then pinned with a 100250-case golden test — it is
   load-bearing product behavior, not incidental code.
2. **Knowledge is accumulated as files, not rows.** The vault is the long-term
   memory. The database holds operational state; the filesystem holds knowledge.

### Where AI actually sits

AI assists at two points: importing tasks from raw material, and the Agent panel
that walks the vault to draft new notes. Both are **legacy-only** and both
currently live in `server/backend_api.py`. The layered `server/ai/` and
`server/services/ai.py` files are placeholders, not implementations. Any claim
that AI drives the core loop is wrong — the deterministic gacha weights do.

## Runtime Architecture

```text
Browser
   ↓  (static/ , served by Flask; index.html at src/index.html)
Flask
   ↓
Legacy backend_api.py                        ← ~3395 lines, DEFAULT ENTRY
   ├─ legacy routes                          ~42 live @app.route
   │    ├─ tasks / gacha / tags / discard    legacy inline handlers
   │    ├─ config / prompts                  legacy inline handlers
   │    └─ Agent / LLM + "/" index route     legacy inline handlers
   │
   ├─ migrated blueprints                    5 registered (inside __main__)
   │    state · schedule · timer · feedback · knowledge
   │    (their legacy twins are commented out)
   │
   └─ services / repositories / schema
          ↓
      SQLite + Obsidian vault
```

The single most important structural fact: **the migrated BPs and the legacy
routes coexist in one process, and the split is incomplete in both
directions.** Three BPs (`tasks`, `gacha`, `tags`) are implemented as real
Blueprints but are *not registered in the default entry* — the legacy inline
versions serve production. Four BP files (`agent`, `config`, `prompts`,
`discard`) contain no `Blueprint` at all; they are lazy re-export shims.

### Registration is asymmetric between the two entries

```text
server/backend_api.py  (DEFAULT)          server/app/app_factory.py
  42 live @app.route                       0 live @app.route
  + state_bp                               + tasks_bp    (9 routes)
  + schedule_bp                            + gacha_bp    (6 routes)
  + timer_bp                               + tags_bp     (4 routes)
  + feedback_bp                            + state_bp   (11 routes)
  + knowledge_bp                           + schedule_bp (8 routes)
                                           + timer_bp    (5 routes)
  = 5 BPs                                  + feedback_bp (3 routes)
                                           + knowledge_bp(9 routes)
                                           + /api/health (inline)
                                           = 8 BPs + 1 route
```

Route counts per BP are read from the `@*_bp.route` decorators.

One consequence worth internalizing: in `backend_api.py` the five
`register_blueprint` calls sit **inside** `if __name__ == '__main__':`. Merely
importing the module yields an app with no blueprints. Any test or tool that
imports `server.backend_api` instead of executing it gets a different app than
the one users run.

## Default Startup

The real chain, end to end:

```text
scripts/启动学习工具.bat
   └─> scripts/start_web_safe.bat
         ├─ resolve interpreter: .venv\Scripts\python.exe
         │   └─ else `py -3 -m venv .venv`
         │       └─ else a non-WindowsApps `python` from PATH
         │           (explicitly skips the Microsoft Store stub)
         ├─ pip install -q -r requirements-web.txt   (Tsinghua mirror on failure)
         ├─ stop any previous instance (stop_web_safe.bat, if .run\server.pid)
         ├─ read port from config/config.json
         └─> scripts/launch_server.py
               ├─ ensure .run\ exists
               ├─ open .run\server.log (append, utf-8)
               ├─ Popen([sys.executable, "server/backend_api.py"], cwd=PROJECT_ROOT)
               ├─ write .run\server.pid
               └─ print "SERVER_PID=<pid>"

       start_web_safe.bat then:
         ├─ poll GET /api/health  (1s interval, max 15 attempts)
         └─ open http://127.0.0.1:<port>/ in the default browser

   ... blocks on `pause` ...
   └─> scripts/stop_web_safe.bat
```

Facts that matter when debugging:

- **`cwd=PROJECT_ROOT`.** The vault path in `config.json` is *relative*
  (`src/notes/vault`), and `knowledge_bp` resolves it against the process CWD.
  Starting `backend_api.py` from the wrong directory yields an empty knowledge
  view — a failure mode indistinguishable from the 5.1 bug.
- Health check is HTTP-200 only. It does not inspect the body, so the two
  different `/api/health` response shapes (below) do not affect startup.
- `.run/server.pid` + `.run/server.log` are the only runtime state, so a stale
  pid file causes the next start to kill the wrong process.

### The other entry

```text
run_app.py
   └─> server.app.create_app()
         ├─ load_config()  (config/config.json, shallow-merged over defaults)
         ├─ Flask(static_folder=_static_dir, static_url_path="/static")
         ├─ CORS(app)
         ├─ app.config["_db_path" | "_notes_dir" | "_project_root"]
         ├─ PRAGMA foreign_keys=ON  ← before schema (a documented P0 fix)
         ├─ configure_sqlite()       ← WAL, busy_timeout 30000ms
         ├─ ensure_all_schema(conn)
         ├─ register 8 blueprints
         └─ define /api/health → {"status": "ok", "phase": 1}
```

`run_app.py` exists to exercise the factory. It is not wired into the `.bat`
launchers, and no production path reaches it.

## Factory Architecture

`create_app()` is the intended end state: config loading, resource wiring, schema
bootstrap, and route registration all in one auditable function, with no
`__main__` guard hiding side effects.

Its current role, stated honestly: **Phase 2 verification entry.** It exists,
it wires a real app, and it is exercised by `scripts/verify_p0_cleanup.py`
(T4 asserts exact per-BP route counts) and by the gacha golden harness.

What it is **not** today:

- not the default entry;
- not route-complete (see Missing parity below);
- not behavior-equivalent to the legacy app.

`_health()` inside the factory returns `{"status": "ok", "phase": 1}`; legacy
`/api/health` returns `{"status": "healthy", "timestamp": ...}`. Two shapes, one
URL. The `"phase": 1` literal is also stale — Phase 2 has been in progress since
2026-08.

### Missing parity (the factory's real gap)

| Area | Factory status | Note |
|---|---|---|
| `tasks` | routes present, **behavior differs** | `unlocked_tasks` hardcoded `[]`; blocked-message gating replaced by a coarser check |
| `gacha` | routes present, **algorithm differs** | `_draw` is `random.choice`; ignores energy, weights, session context; `replace` does not log rejection nor redraw |
| `tags` | routes present | no known divergence |
| `state` / `schedule` / `timer` / `feedback` / `knowledge` | migrated, registered in **both** entries | these are the safest modules |
| Agent (9 routes) | **absent** | `agent_bp` has no `Blueprint`; logic remains legacy-only |
| Prompts (5) | **absent** | `prompts_bp` is a shim |
| Config (2) | **absent** | `config_bp` is a shim |
| Discard (3) | **absent** | `discard_bp` is a shim |
| `/api/dependencies`, `/api/export`, `/` | **absent** | legacy-only |

E2E cases 6.3 (prompt browsing) and 6.4 (Agent panel) depend on routes the
factory does not serve — so factory coverage cannot be judged by "the E2E is
green".

The gacha golden test must not be misread as closing this gap: it compares
**weight functions**, not the routes that consume them. Route parity for gacha
is unverified and, on code inspection, not equivalent.

## Backend Layers

Current real layering, per module. "Real" = contains its own logic. "Shim" =
lazy re-export of `backend_api`.

### Blueprint — HTTP boundary

```text
server/blueprints/
  _common.py        json_error / json_ok helpers
  tasks_bp.py       9 routes   REAL, but not registered in default entry
  gacha_bp.py       6 routes   REAL, but simplified algorithm
  tags_bp.py        4 routes   REAL
  state_bp.py      11 routes   REAL — registered in both entries
  schedule_bp.py    8 routes   REAL — registered in both entries
  timer_bp.py       5 routes   REAL — registered in both entries
  feedback_bp.py    3 routes   REAL — registered in both entries
  knowledge_bp.py   9 routes   REAL — registered in both entries
  agent_bp.py       —          SHIM (no Blueprint; "Do NOT register")
  config_bp.py      —          SHIM
  prompts_bp.py     —          SHIM
  discard_bp.py     —          SHIM
```

Two package-level design rules are load-bearing:

- `server/blueprints/__init__.py` must **not** eagerly import the shim modules.
  Each shim does `from server import backend_api`, which would drag the entire
  3395-line monolith (Flask app, 42 routes, schema, gacha side effects) into any
  import of the package. The shims are therefore resolved lazily through PEP 562
  `__getattr__`. This was a documented P0 near-miss ("BOMBSHELL bug 3"), and
  `verify_p0_cleanup.py` T1–T3 exist specifically to keep it fixed.
- BP modules reach the DB through `current_app.config` + a shared
  `make_request_conn()` helper, never by importing `backend_api` directly —
  which is what makes the factory able to host them at all.

### Service — pure business logic, no Flask

```text
server/services/
  gacha.py      REAL — the weighted algorithm behind a GachaAlgo Protocol,
                 parameterized so the algorithm can be swapped without touching BPs
  state.py      REAL
  timer.py      REAL
  feedback.py   REAL
  knowledge.py  REAL — vault walking, category maps, link resolvers, graph builder
  schedule.py   PARTIAL — only the 10-slot day template constant
  ai.py         EMPTY PLACEHOLDER (__all__ = [])
```

Services take their vault root / DB path as **arguments** rather than reading
globals. That is what lets the same code run under either entry, and it is why
`knowledge.py` is parameterised by `notes_dir` instead of closing over a module
constant.

### Repository — SQL and filesystem access

```text
server/repositories/
  state_repo.py        REAL  (180 lines)
  timer_repo.py        REAL  (154 lines)
  schedule_repo.py     REAL  (143 lines)
  feedback_repo.py     REAL  (96 lines)
  note_index_repo.py   REAL  — pure filesystem: md counts, category list, recent
  task_repo.py         SHIM  — 10 passthroughs to backend_api
  gacha_repo.py        SHIM  — 2 passthroughs
```

The shims are honest about being transitional. Note `note_index_repo` is a
*filesystem* repository — knowledge access never touches SQLite, which is a
direct consequence of "knowledge lives in the vault".

`note_index_repo.recent_notes()` returns four hardcoded entries, preserved
verbatim from the legacy handler with a "P3 known issue" marker. Same for the
fallback counts `linear=8` / `computer=6` in `list_categories()`. These are
**known preserved quirks, not bugs to fix in passing** — changing them changes
API output.

### Schema — DDL

```text
server/schema/
  __init__.py   ensure_all() — idempotent, applied at startup in both entries
  tasks.py  gacha.py  state.py  feedback.py  notes.py
```

`ensure_all` is idempotent and runs on every start in both entries, so schema
presence is never a startup blocker. `create_app()` sets
`PRAGMA foreign_keys=ON` *before* calling it, so FK clauses in the DDL are
actually enforced — otherwise SQLite's default `foreign_keys=OFF` would silently
permit orphans. T6 of the P0 script guards this.

### Legacy compatibility layer

`server/backend_api.py` is simultaneously four things: the default application,
the domain model, the parity oracle, and a compatibility shim for modules that
still import from it.

It also holds the migration switch: four blocks are marked
`PHASE 2 TODO n ..._MIGRATION_START/END` with their `@app.route` decorators
**commented out** (knowledge 9, schedule 8, state 6, feedback 3). Commenting
rather than deleting is deliberate — it keeps the original text as the
comparison reference and avoids Flask double-registering the same URL. The
matching `TODO(phase2-todo12): delete this entire block` markers record that
removal is still owed.

Two loose ends in this layer:

- `knowledge_bp` keeps a `__getattr__` map from old `api_*` names to the new
  BP view functions, purely to satisfy `verify_p0_cleanup.py` T3, which asserts
  that touching a stub attribute fires the `backend_api` import. That is a
  **test-shaped constraint baked into production code**, self-documented as such
  ("Will be removed once verify_p0_cleanup.py T3 is updated").
- `gacha_bp._conn()` keeps an `os.path.join(...)` fallback for the case
  where `_db_path` is absent. `gacha_bp.py` now imports `os`, so the former
  latent `NameError` is fixed. The branch is still low-coverage because the
  factory sets `_db_path` and the legacy entry does not register `gacha_bp`.

## Frontend

A **local web app with native JavaScript and no bundler, no build step, and no
framework.** `index.html` loads scripts with plain `<script src>`; the only
module is one thin bootstrap. There is nothing to compile, and nothing that
transpiles or resolves imports.

Load order in `src/index.html` is the architecture:

```text
/static/vendor/marked.min.js
/static/core/event-bus.js       ├─ loaded BEFORE app.js, expose window.SAL.core.*
/static/core/api.js              │
/static/core/ui.js              │   all global scripts — no imports
/static/core/theme.js           │   they attach to a shared namespace
/static/core/router.js          │
/static/core/theme-init.js      │
/static/app.js            ← ~2674 lines, the real UI
/static/app.entry.js      ← type="module", thin bootstrap, runs LAST
```

Two additional core files exist but are **not currently loaded by `src/index.html`**:
`static/core/state.js` and `static/core/constants.js`. `app.entry.js` probes
their namespaces in its boot report, so they currently appear as missing rather
than participating in runtime behavior.

Two truths about the frontend, and the second is easy to get wrong:

1. The modular scaffolding exists, but only the six core scripts shown in the
   load-order block above are currently loaded before `app.js`.
2. **The frontend migration is not done.** `app.entry.js` says so itself: it
   wires nav clicks to the event bus and prints a boot report, and its
   `page:change` listener is an explicit noop awaiting "Phase 3". `modules/*`
   (48 and 37 lines) are placeholders that do not take over. `app.js` remains
   the only owner of the UI.

Treat `static/core`, `static/shared`, and `static/modules` as *scaffolding that
is present and harmless*, not as a modularized codebase.

The backend serves `/` by reading `index.html` from the project root, falling
back to `src/index.html`, and sends `no-cache` so edits show up on reload. Note
the file physically lives in `src/` — a legacy of the desktop era, handled by
that dual-candidate lookup rather than by moving it.

## Persistence

Two stores, with a hard separation of concerns.

### SQLite — operational state

```text
data/task_publisher.db   (+ .db-wal, .db-shm in WAL mode)
```

Tables cover tasks (with `prerequisite_ids` as a JSON column), `task_dependencies`,
`task_tags`, `tags`, `gacha_records`, `task_rejection_log`, schedule
activities, timer sessions, daily tone / energy / sleep state, and state
assessment history.

Connection discipline, enforced in `server/extensions.py::make_request_conn()` and
mirrored by a legacy `configure_sqlite()`:

```text
PRAGMA journal_mode = WAL
PRAGMA foreign_keys = ON
PRAGMA busy_timeout = 30000   (30 s)
row_factory = sqlite3.Row
```

The 30 s busy timeout is what keeps concurrent writers from failing fast; WAL is
what allows a reader (a running server) alongside a writer (a test). This is
also why `.db`, `.db-wal`, and `.db-shm` are a single state unit — see
`docs/CURRENT_PROJECT_STATE.md` § Data Safety.

Gaps are handled by the code, not by the schema: `tasks_bp` computes
`is_unlocked` from prerequisite completion on write, and `task_dependencies`
is the normalized table used only by the dependents query, while
`prerequisite_ids` JSON remains the primary edge store read by the dependency
graph. Two representations of the same relationship coexist.

### Obsidian vault — knowledge

```text
src/notes/vault/     ← config: obsidian.notes_directory (a RELATIVE path)
```

Markdown on disk is the system of record for knowledge. Access is read-only
plus one shell-out: `POST /api/knowledge/open-in-obsidian` spawns the
`obsidian://open?path=...` URI via `subprocess.Popen(["start", ...])`. That
side effect is intentionally placed in the BP layer rather than the service
layer, so services stay pure.

The vault is gitignored (`.gitignore:68`) — **it is real user data, and it is
not in version control.** The only thing the repo holds is any `.zip` explicitly
un-ignored on line 69.

## Knowledge Architecture

One Blueprint (`knowledge_bp`, 9 routes) over one service (`knowledge.py`) over
one filesystem repository (`note_index_repo.py`).

```text
GET  /api/knowledge/categories          5 fixed subjects + live .md counts
GET  /api/knowledge/points?category=    knowledge points, optionally per subject
GET  /api/knowledge/graph               nodes + links from [[wiki]] and md links
GET  /api/knowledge/note/<path>         single note content
GET  /api/knowledge/recent              4 HARDCODED entries (known P3 issue)
GET  /api/knowledge/notes               notes at vault root, one level deep
GET  /api/knowledge/note-content/<path> note content + path
GET  /api/knowledge/point-detail/<subj>/<name>
POST /api/knowledge/open-in-obsidian   shell spawn (BP-layer side effect)
```

The graph builder is the most substantial piece. It walks the vault, indexes
paths and filename stems, then resolves links three ways: wiki links
(`[[target|alias]]`, `[[target#heading]]`), relative markdown links, and
bare-filename matches against the stem index. Category attribution comes from
`_note_category()`: it returns the second path segment when the first segment is
`知识点`, otherwise the first segment.

### Dual vault layout — unresolved

The vault currently holds **two populated, competing layouts**, and the
knowledge endpoints are split across them:

```text
<notes_dir>/<subject>/*.md              →  /api/knowledge/notes        ≈172 notes
<notes_dir>/知识点/<subject>/*.md        →  categories / points / detail ≈1307 notes
```

Top-level directories present: `.obsidian`, `知识点`, `已分类`, `未分类`,
`高等数学`, `大学物理`, `电子技术`, `计算机`, `英语四级`, `diagrams`.

This is **DUAL VAULT LAYOUT — UNRESOLVED PRODUCT/DATA CONTRACT.** Both layouts
are live, served by different endpoints, and the graph's category logic
special-cases one of them. Nothing in the codebase or config declares which
layout is canonical, and which one is "correct" is a product decision — not
something to be resolved by whichever agent looks at it next. Do not consolidate,
delete, or migrate either layout without an explicit decision.

For scale, the current verified dataset returns **≈172** notes from
`/api/knowledge/notes` under the default legacy runtime. That is a property of
the data, not an invariant to assert against.

## Migration Boundary

### Nothing below may be deleted yet

| Asset | Why it must stay |
|---|---|
| `server/backend_api.py` | default entry **and** the parity oracle for tasks/gacha parity; the four comment-out blocks are the reference text. Removal before equivalence is proven destroys the only baseline. |
| Commented-out legacy route blocks | the pre-migration behavior of 26 routes. Deleting them removes the comparison target. |
| Shim BP modules (`agent`, `config`, `prompts`, `discard`) | sole import path for 19 legacy-only routes. |
| `task_repo.py`, `gacha_repo.py` passthroughs | active call path today, transitional by design. |
| `knowledge_bp.__getattr__` legacy-name map | satisfies `verify_p0_cleanup.py` T3; removing it without updating that script turns a green P0 into a red one. |
| `note_index_repo` hardcoded recent-notes + fallback counts | preserved legacy output; changing them changes API responses. |
| `src/notes/**` (real vault) | user data, gitignored, and holds the unresolved dual layout. |
| `data/task_publisher.db` (+ `-wal`, `-shm`) | real user state; the triple is one atomic unit. |
| `config/config.json` | port, relative vault path, API keys. Relative path + CWD dependency makes it load-bearing. |

### Rules that follow from the current shape

- Do not switch the default entry to `run_app.py` until the factory serves the
  full route surface with verified-identical behavior. Cases 6.3 and 6.4 already
  fail without it.
- Do not treat the gacha golden pass as evidence of route parity. It tests
  weights; the routes are a different implementation.
- Do not "clean up" the lazy-import machinery in `blueprints/__init__.py`. It is
  the fix for a known import-time bomb, guarded by T1–T3.
- Do not resolve the dual vault layout by picking a side.
- Do not normalize SQLite without treating `.db` + `.db-wal` + `.db-shm` as one
  unit.
- Do not start the server from a different working directory. The vault path is
  relative, and the failure looks exactly like the 5.1 bug.

1. This file — the shape of the system.
2. `docs/CURRENT_PROJECT_STATE.md` — health, baselines, and the ordered plan.
3. `server/app/app_factory.py` — the intended end state, small enough to read
   in one pass.
4. `scripts/启动学习工具.bat` → `start_web_safe.bat` → `launch_server.py` — the
   chain you will actually run.
5. `server/backend_api.py` — last, and selectively. It is 3395 lines, and much of
   it is commented-out history.
6. `tests/e2e-manual.js` — the 36 cases that define "working".

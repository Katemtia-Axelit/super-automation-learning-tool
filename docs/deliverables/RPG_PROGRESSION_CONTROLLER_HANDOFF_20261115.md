## 1. 本轮工作是什么

围绕「在现有超级自动化学习工具上建立 RPG 成长与能力反馈模块」进行了多轮产品讨论，并与 Gemini 进行了连续方案评审、反例审查和产品决策收敛。

讨论重点从最初的任务面板、经验和货币正反馈，逐步聚焦到一个核心命题：

**正式 EXP 必须尽可能诚实地反映用户由可信证据支持的真实能力，而不能把学习投入、任务勾选或 AI 的主观认可伪装成能力成长。**

最终已完成产品哲学、能力图谱、证据模型、双轨奖励、考核与校准、等级、初始定级以及跨模块职责边界的收敛。

## 3. 已冻结的关键决定

### 3.1 EXP 与能力模型

- EXP 是基于可信证据的当前能力估值，不由看课时长、学习时长或 Task 勾选直接产生。
- Action、Evidence、Progression 三者分离。
- 采用 Domain → Capability Cluster → Capability Unit（CU）→ Observable Criteria（OC）四层逻辑图谱。
- CU 是正式 EXP 估值单元；OC 是最小能力证据锚点。
- CU 在用户全局能力库中唯一，可跨 Quest、Campaign、Domain 引用。
- 多个 Domain 的 EXP 是领域投影，不能简单相加为全局独立能力总分。
- 能力图谱按需渐进生长；当前 Quest 启动前，其关联 OC 和验收标准必须明确。
- 拆分既有 CU 时，子单元基准权重继承原单元；真正新增的独立能力允许扩容。
- 节点拆分时，历史证据只迁移到实际支持的新 OC；无法支持的部分标记待重新验证。

### 3.2 能力证据

- 能力表现维度与证据质量属性分离。
- 采用受控通用维度池，由领域和 CU 选配，不强迫所有学科使用同一画像。
- 文档、IDE 补全等正常工具不自动扣分。
- AI 辅助是否有效取决于当前 OC 的目标能力；不采用统一 AI 扣分系数。
- 一份 Evidence 可以映射多个 CU / OC，但每个映射必须有独立的实际参与和验收依据。
- 任务 DAG 依赖关系不自动构成上游能力证据。
- 同构重复练习不线性增加证据充分性。

### 3.3 双轨奖励与考核闭环

- 行动正反馈与能力 EXP 双轨分离。
- 完成任务可以获得任务状态、Quest 推进和行动货币，但不自动获得 EXP。
- Core OC 未通过只阻止 CU 获得 Mastered 和相关等级认证，不得对整个 CU EXP 严厉封顶。
- Task、Assessment、Capability 是三个独立状态维度。
- 普通练习考核失败，只要用户完成了实际练习或提交，Task 仍可完成并按规则获得行动奖励；Assessment 记录失败，能力不被错误标记为掌握。
- 独立考核卡完成实质性提交后，无论通过与否，卡片实例都必须结束并归档，不得永久卡在待办列表。
- 独立考核首次有效尝试可以领取一次行动奖励；空白、无关提交或秒退不构成有效尝试。
- 同一考核目标只能领取一次首次有效尝试奖励；Re-test Card 不重复发行动货币；补强训练卡按实际工作量正常奖励。
- 任务拆分不能凭空创造货币预算；真实失败不追回此前诚实完成任务的行动奖励。

### 3.4 校准与等级

- 时间流逝不直接扣 EXP；证据长期缺失可进入待校准状态。
- 区分偶然失误、真实遗忘、历史评估虚高和重新证明。
- 真实遗忘下调 Current EXP，但保留真实 Peak EXP。
- 历史证据被证伪时，Current EXP 与 Peak EXP 都按有效历史重算；依赖无效核心证据的 Peak Level 也应重新计算，撤销历史仍留痕。
- Domain Level 由领域 EXP、必达核心 CU 的 Mastered 状态，以及该领域适用的综合能力要求共同决定。
- 等级不是一刀切任务权限门禁；具体任务准入看实际 DAG 和能力依赖。
- Synthesis CU 只表达底层 CU 无法表达的独立综合能力，按学科适配，不强制所有 Domain 采用统一模板。
- 初始能力探测与日常验证使用相同证据标准，已证明能力可跳过相应基础内容。

### 3.5 模块边界

- Quest / Task：规划成长路线、任务串和具体行动。
- Gacha：从可执行任务中选择行动，降低启动阻力。
- Assessment：组织考核并生成证据。
- Progression：维护能力状态、EXP、等级和校准需求。
- AI：生成草案、考核内容、结构化分析和能力缺口建议。
- 确定性代码：执行正式状态、EXP、等级和货币结算。
- UI：分别呈现行动反馈和能力反馈，提供证据溯源。

Progression 不接管 Quest 编排，也不接管 Gacha 的抽卡算法。

## 6. 给主控的建议接手顺序

请按依赖关系线性推进，不要直接并行派发互相依赖的模块开发。

1. **先阅读产品规范**：以 docs/RPG_PROGRESSION_PRODUCT_SPEC_V1.0.md 为 RPG 产品决策来源。
2. **审计现有实现**：核验当前真实运行入口、Quest/Task 数据模型和状态流、Gacha 候选池及抽取规则、行动奖励现状、AI 任务生成入口、UI 页面和数据库结构。
3. **建立映射矩阵**：逐项标记「已有能力可复用 / 需要扩展 / 尚不存在 / 与产品规范冲突」。
4. **先确定集成边界**：确认 Progression 从哪些现有事件消费数据、向 Quest/UI 输出什么；避免重复实现任务和抽卡。
5. **再形成工程架构方案**：模块边界、概念实体、事件流、数据迁移策略、幂等与审计方案。
6. **最后按主控批次派发开发**：一个批次完成并留下可交接证据后，再推进其依赖的下一批次。

## 7. 工程接手时的注意事项

- 项目现有 docs/ARCHITECTURE.md 与 docs/CURRENT_PROJECT_STATE.md 包含带日期的架构快照和增量说明；不要把历史 Snapshot 当成当前运行事实。
- 以当前源码、真实运行入口和独立验证结果为准。
- 不要假定当前 Task 已经具有 CU / OC 关联能力。
- 不要假定当前 Gacha 已有校准卡专用机制；产品要求是校准卡作为正常候选任务，不是另造抽卡系统。
- 不要假定当前行动货币账本已经支持同目标限领、拆卡预算守恒或幂等纠错。
- 不要把本规范中的概念实体直接机械地一对一映射为数据库表。
- 不要在工程审计前确定 SQL 结构或直接大规模改动源码。
- 保持现有项目的保护边界；任何真实用户数据、知识库和生产配置的操作都应明确限定范围并留痕。
